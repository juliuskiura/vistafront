# Next.js App Router Migration Plan: frontapp → vistafront

## Objective

Transform vistafront (Next 16.3.4, React 19, Tailwind v4) into a **proper Next.js App Router application** — not an SPA port. This is a **rebuild using Next.js patterns**, not a reconciliation of the Vite SPA architecture.

`frontapp` (Vite SPA) is **reference only**. We extract **domain knowledge and business logic**, NOT architecture patterns.

### Non-Negotiable Principles

1. **Server Components are the default** — Every page/layout starts as a Server Component. Add `"use client"` ONLY when hooks or browser APIs are required.

2. **Server-side data fetching** — All data comes from Server Components or Server Actions. No client-side fetching except for real-time/interactive features that cannot be server-rendered.

3. **Server Actions for mutations** — All writes (login, create, update, delete) use Server Actions. No client-side mutation logic.

4. **No Redux for server state** — Server data is not stored in client state. React Context + `useState`/`useReducer` for UI state only (sidebar, modals, toasts).

5. **No navigation bridges** — `redirect()` in Server Components, `useRouter()` in Client Components. Never `window.location.assign` or global navigator patterns.

6. **HttpOnly cookies for auth** — JWT tokens stay in HttpOnly cookies set by Django. Server Components read cookies; client never touches tokens.

7. **Progressive enhancement** — Forms work without JavaScript. Server Actions provide this by default.

## Architecture Decision Record

### Data Fetching Strategy

| Scenario | Solution |
|----------|----------|
| Page initial data | Server Component `fetch()` with Next.js cache |
| User-specific data | Server Component reads cookies, fetches with forwarded auth |
| Interactive/real-time data | TanStack Query in Client Components (rare) |
| Search/filter/pagination | Server Component with searchParams, or Server Actions |

### State Management Strategy

| State Type | Solution |
|------------|----------|
| Server data | No client state — fetch in Server Components |
| Auth user | Server Component reads cookie, passes to layout |
| UI state (sidebar, modal) | React Context + `useState` |
| Form state | Server Actions + `useFormState` (or Zod validation) |
| Toasts | React Context or Server Action return values |
| Workspace selection | Server Component passes workspace from cookie/path |

### Routing & Navigation

| Context | Method |
|---------|--------|
| Server Component | `redirect("/path")` |
| Server Action | `redirect("/path")` after mutation |
| Client Component event | `const router = useRouter(); router.push("/path")` |
| Client Component effect | `useEffect(() => router.push(...))` |

**Forbidden:** `window.location.assign`, `window.location.href`, global navigator bridges, navigation from non-component code.

#### F3: Server-Side Data Fetching Utilities

**Goal:** Standardized patterns for fetching from Django in Server Components.

**Tasks:**
1. Create `lib/api/fetcher.ts`:
   ```typescript
   export async function serverFetch<T>(
     path: string,
     options?: RequestOptions
   ): Promise<T> {
     const cookieStore = await cookies();
     const access = cookieStore.get("access");
     
     const response = await fetch(`${process.env.BACKEND_URL}${path}`, {
       headers: {
         Cookie: `access=${access?.value}`,
         "Content-Type": "application/json",
       },
       cache: options?.cache ?? "no-store",
       next: options?.next,
     });
     
     if (!response.ok) {
       throw new ApiError(response.status, await response.text());
     }
     
     return response.json();
   }
   ```

2. Create `lib/api/types.ts`:
   - TypeScript types for all API responses (extracted from frontapp)
   - `Workspace`, `User`, `Project`, etc.

3. Create domain-specific fetchers:
   - `lib/api/workspaces.ts` — `getWorkspaces()`, `getWorkspace(slug)`
   - `lib/api/users.ts` — `getCurrentUser()`, `updateUser()`
   - etc.

**Verification:**
- All API calls go through `serverFetch`
- Types are complete and match Django models
- No RTK Query imports

   "use client";

     isOpen: boolean;
     toggle: () => void;
   }>(...);

## Critical Rules (Add to AGENTS.md)

1. **Never use `window.location`** — Use `redirect()` or `useRouter()`.

2. **Never fetch in `useEffect`** — Fetch in Server Components.

3. **Never store server data in client state** — Let the server own it.

4. **Never use Redux for API state** — Server Components + React Query (rare) only.

5. **Server Actions for all mutations** — No client-side POST/PUT/DELETE.

6. **Auth decisions on the server** — Read cookies in Server Components, redirect if invalid.

7. **Progressive enhancement** — Forms must work without JavaScript.

8. **Client Components are opt-in** — Default to Server Components.
